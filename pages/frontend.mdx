# Frontend

The storefront is a **single-page** experience built with **HTML, CSS, and JavaScript** — no framework, no build step. It talks to the backend REST API using **JWT authentication** and uploads product images directly to **AWS S3** using presigned URLs.

## Files

| File | Role |
|------|------|
| `index.html` | Layout — hero, OTP/admin auth card, shop, cart, orders, admin panel, file-input on the admin form |
| `style.css`  | Dark luxury theme (gold accents, responsive layout), branded auth card, status badges |
| `script.js`  | API calls, OTP + admin auth, `IS_ADMIN_SITE` gating, three-step S3 upload, UI state, image/emoji fallback |

## API base URL

```javascript
const API = (location.protocol === 'file:' || location.port === '5500' || location.port === '3000')
  ? 'http://localhost:8080/api'
  : '/api';
```

When deployed under nginx (`gotokart.xyz` / `admin.gotokart.xyz`), the relative `/api` path is reverse-proxied to the backend container. Locally (Live Server / file), it points straight at Spring Boot on port 8080.

## One app, two domains

The same SPA is served on both the storefront and the admin domain. A single flag drives the difference:

```javascript
const IS_ADMIN_SITE = location.hostname.startsWith('admin.');
```

- **`gotokart.xyz`** — storefront. Login is **email OTP**. The admin panel and its nav links are always hidden, even for `ADMIN` accounts.
- **`admin.gotokart.xyz`** — admin only. Login is **email + password** via `/api/auth/admin/login`; non-admins are rejected and the storefront nav is stripped.

## Authentication

The frontend uses **JWT tokens** stored in `localStorage` (`gk_token`).

**Customer OTP login (storefront)** — a two-step, passwordless flow:

1. `POST /api/auth/otp/request` `{ email }` — emails a 6-digit code
2. `POST /api/auth/otp/verify` `{ email, otp, name? }` — verifies and returns a JWT

**Admin login (admin domain)** — `POST /api/auth/admin/login` `{ email, password }`.

- Session is automatically restored from `localStorage` on page reload (`GET /api/users/me`).
- Requests include `Authorization: Bearer <token>` via a small `authHeaders()` helper.

**Default admin account**

- Email: `admin@gotokart.xyz`
- Password: `admin123`

## Features (overview)

- Passwordless **email OTP** login with resend cooldown; polished, branded auth card
- Dedicated **admin domain** (`admin.gotokart.xyz`); admin panel never appears on the storefront
- Product listing with search, filters, sorting, and category tags
- Auto emoji detection for 150+ product types (used as a fallback when there's no image)
- **Admin-only image upload to S3 via presigned PUT** (max 1 MB · JPG / PNG / WEBP)
- Cart with quantity stepper and real-time totals
- Place order and view order history; admins manage status (`Placed → Shipped → Out for delivery → Delivered`)
- A **Test Email** button in the admin dashboard to verify SMTP delivery

## Image upload flow

The browser does the heavy lifting. The backend only signs URLs.

```text
[Admin form submit]
       │
       │ 1. POST /api/products            ──▶ { id, name, … }
       │
       │ 2. POST /api/products/{id}/image-upload-url?contentType=image/png
       │                                   ──▶ { url, key, contentType, publicUrl, … }
       │
       │ 3. PUT <url>   Content-Type: image/png   body=fileBytes
       │     (CORS preflight goes straight to S3, never touches the API)
       │                                   ◀── 200 OK
       │
       │ 4. PATCH /api/products/{id}/image   { imageKey: key }
       │                                   ──▶ updated product (old S3 object deleted)
       ▼
   product card now shows <img src="publicUrl"/>
```

### Why this pattern?

- **No JVM bytes** — Spring Boot never sees the image, so we don't pay memory, time, or bandwidth for them.
- **Short-lived URLs** — every upload uses a fresh URL that expires in 5 minutes, signed by the backend's IAM role.
- **Strict content type** — the backend signs against the exact MIME type the client claims, and S3 rejects the PUT if the request header doesn't match.
- **Old image cleanup** — `PATCH /api/products/{id}/image` and `DELETE /api/products/{id}` both clean up the previous S3 object so you never accumulate orphans.

### Rendering

`script.js` exports two small helpers:

```javascript
function productImageUrl(p) {
  if (!p?.imageKey) return null;
  return `https://${BUCKET}.s3.${REGION}.amazonaws.com/${p.imageKey}`;
}

function productVisual(p) {
  const url = productImageUrl(p);
  return url
    ? `<img class="product-image" src="${url}" alt="${escapeHtml(p.name)}" loading="lazy"/>`
    : `<div class="product-emoji">${categoryEmoji(p)}</div>`;
}
```

If `imageKey` is missing, the storefront falls back to the category emoji — the user never sees a broken image.

### Admin form

```html
<div class="form-group" style="grid-column:1/-1">
  <label>Product Image (optional, max 1 MB — JPG / PNG / WEBP)</label>
  <input type="file" id="pImage" accept="image/jpeg,image/png,image/webp" class="input"/>
  <small>Uploaded directly to AWS S3 via a presigned URL.</small>
</div>
```

`addProduct()` saves the product first, then — if a file was selected — calls `uploadProductImage(savedId, file)` which performs steps 2–4 above.
