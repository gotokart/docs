# Infrastructure

Full deployment reference for GoToKart on AWS EC2 — domain, TLS, Docker, S3, IAM, and the day-to-day runbook. See the [`infra` repo](https://github.com/gotokart/infra) for all config files referenced here.

## Live deployment

| | |
|-|-|
| **Storefront**     | <code>https://gotokart.xyz</code> · <code>https://www.gotokart.xyz</code> |
| **API**            | <code>https://gotokart.xyz/api/</code> |
| **HTTP**           | 301-redirected to HTTPS (except `/.well-known/acme-challenge/`) |
| **TLS issuer**     | Let's Encrypt (ECDSA), webroot challenge |
| **Auto-renewal**   | `gotokart-cert-renew.timer` — twice daily on EC2 |

### EC2 instance

| Field | Value |
|-------|-------|
| **Status**       | Active |
| **Name**         | `gotokart-ecommerce` |
| **Type**         | `t3.small` (2 vCPU, 2 GB RAM, 2 GB swap) |
| **Region**       | `us-east-1` (N. Virginia) |
| **OS**           | Amazon Linux 2023 |
| **Public IP**    | `52.90.87.237` (the DNS A records for `gotokart.xyz` / `www.gotokart.xyz` point here) |
| **IAM role**     | `ec2-role-iam` — provides credentials for S3 (no static keys on the box) |

### Docker — two containers

| Role | Service | Port | Notes |
|------|---------|------|-------|
| Frontend | nginx (alpine) | 80 → 443 | Terminates TLS, serves static frontend, reverse-proxies `/api/*` |
| Backend  | Spring Boot (Java 21) | internal :8080 | Signs S3 presigned URLs, talks to RDS over JDBC |

**Network:** `infra_gotokart-net`
**Cert volumes:** `./certs` (read-only into nginx) · `./certbot-webroot` (read-only into nginx, writable by certbot service unit)

### Database — AWS RDS (managed)

| Field | Value |
|-------|-------|
| Service | Amazon RDS for MySQL 8.0 |
| Instance identifier | `gotokart-db` |
| Endpoint | `gotokart-db.xxxxxxxx.us-east-1.rds.amazonaws.com:3306` |
| Database name | `gotokart` |
| App user | `gotokart_app` (granted `ALL` on `gotokart.*`) |
| Public access | **No** — private to the VPC |
| Encryption | At-rest (KMS) + in-transit (TLS, JDBC `useSSL=true&requireSSL=true`) |
| Backups | Automated, 7-day retention |

The backend reads the connection details from `infra/.env` (see [AWS RDS setup](#aws-rds--one-time-setup) below). There is **no database container** in production any more.

The two runtime containers sit on a single EC2 host, connected via the `infra_gotokart-net` bridge network. Only nginx is exposed to the internet (ports 80 + 443). The backend signs S3 PUT URLs using credentials supplied by the EC2 instance profile — there are no AWS access keys anywhere on disk. The database lives in **AWS RDS** and is reachable from EC2 over the private VPC network only.

## TLS — Let's Encrypt + nginx (webroot mode)

`nginx.conf` listens on both 80 and 443. Port 80 redirects everything to HTTPS **except** `/.well-known/acme-challenge/`, which is served from a webroot volume that certbot writes into:

```nginx
server {
    listen 80;
    server_name gotokart.xyz www.gotokart.xyz;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl;
    server_name gotokart.xyz www.gotokart.xyz;

    ssl_certificate     /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;
    # … gzip / proxy_pass / static config …
}
```

### First-time issuance

```bash
sudo certbot certonly --webroot \
  -w /home/ec2-user/gotokart/infra/certbot-webroot \
  -d gotokart.xyz -d www.gotokart.xyz \
  -m you@example.com --agree-tos --no-eff-email
```

Then copy `fullchain.pem` and `privkey.pem` from `/etc/letsencrypt/live/gotokart.xyz/` into `infra/certs/` and `docker compose restart nginx`.

### Auto-renewal (systemd timer)

`/usr/local/bin/gotokart-cert-renew.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail
certbot renew --quiet --deploy-hook 'install -m 644 \
  /etc/letsencrypt/live/gotokart.xyz/fullchain.pem \
  /etc/letsencrypt/live/gotokart.xyz/privkey.pem \
  /home/ec2-user/gotokart/infra/certs/ && \
  docker exec gotokart-nginx nginx -s reload'
```

Paired with a unit + timer:

```ini
# /etc/systemd/system/gotokart-cert-renew.service
[Unit]
Description=Renew Let's Encrypt certs for gotokart.xyz
[Service]
Type=oneshot
ExecStart=/usr/local/bin/gotokart-cert-renew.sh
```

```ini
# /etc/systemd/system/gotokart-cert-renew.timer
[Unit]
Description=Twice-daily certbot renew for gotokart.xyz
[Timer]
OnCalendar=*-*-* 03:17,15:17:00
RandomizedDelaySec=30m
Persistent=true
[Install]
WantedBy=timers.target
```

```bash
sudo systemctl enable --now gotokart-cert-renew.timer
sudo systemctl list-timers | grep gotokart
sudo systemctl start gotokart-cert-renew.service   # one-time dry-run check
```

If certbot was originally issued with `--standalone`, switch the renewal config to webroot once:

```bash
sudo sed -i 's/^authenticator = standalone$/authenticator = webroot/' /etc/letsencrypt/renewal/gotokart.xyz.conf
echo 'webroot_path = /home/ec2-user/gotokart/infra/certbot-webroot,' | \
  sudo tee -a /etc/letsencrypt/renewal/gotokart.xyz.conf
sudo certbot renew --dry-run
```

Full runbook lives in `infra/certs/README.md`.

## AWS RDS — one-time setup

GoToKart's database lives in **Amazon RDS for MySQL 8.0**, not in a container. The backend connects to it over JDBC using credentials supplied by `infra/.env` on the EC2 host. RDS handles patching, backups, and storage scaling.

### 1. Provision the RDS instance

In the AWS Console: **RDS → Create database → Standard create**.

| Setting | Value |
|---------|-------|
| Engine | MySQL 8.0 (latest minor) |
| Template | Production (or Dev/Test for non-prod) |
| DB instance identifier | `gotokart-db` |
| Master username | `admin` (used only to create the app user below) |
| Master password | store in a password manager |
| Instance class | `db.t4g.micro` (sufficient for low traffic) |
| Storage | 20 GB gp3, autoscaling enabled |
| VPC | Same VPC as the EC2 host |
| Public access | **No** |
| VPC security group | new `gotokart-rds-sg` |
| AZ | Same AZ as EC2 (lower latency, no cross-AZ charges) |
| Initial database name | `gotokart` |
| Backups | 7-day retention |
| Encryption | Enabled (KMS default key) |

### 2. Tighten the RDS security group

`gotokart-rds-sg` inbound rules:

| Type | Port | Source |
|------|------|--------|
| MySQL/Aurora | 3306 | The EC2 security group (`sg-xxxxxxxx`) |

No public CIDRs, no `0.0.0.0/0`. Outbound rules can stay default.

### 3. Create a least-privilege application user

From the EC2 host (which has VPC reach to the RDS endpoint):

```bash
mysql -h gotokart-db.xxxxxxxx.us-east-1.rds.amazonaws.com -u admin -p
```

```sql
CREATE USER 'gotokart_app'@'%' IDENTIFIED BY 'a-strong-password';
GRANT ALL PRIVILEGES ON gotokart.* TO 'gotokart_app'@'%';
FLUSH PRIVILEGES;
```

The backend will use `gotokart_app` exclusively. Never put the master `admin` credentials in `infra/.env`.

### 4. Wire up `infra/.env`

On EC2:

```bash
cd /home/ec2-user/gotokart/infra
cp .env.example .env
nano .env
```

Fill in `RDS_HOST`, `RDS_USERNAME`, `RDS_PASSWORD`, and `JWT_SECRET`. The compose file substitutes these into the backend container's `SPRING_DATASOURCE_URL` automatically. `infra/.env` is git-ignored (`.gitignore` already covers `.env` and `*.env`).

### 5. (Optional) migrate from the old MariaDB container

If you previously ran the in-container MariaDB and want to keep the data:

```bash
# On EC2, before bringing down the old stack
docker exec gotokart-mysql mariadb-dump -uroot -pRoot@1234 gotokart > gotokart-dump.sql

# Push the dump into RDS
mysql -h gotokart-db.xxxxxxxx.us-east-1.rds.amazonaws.com -u gotokart_app -p gotokart \
  < gotokart-dump.sql
```

Otherwise JPA's `ddl-auto=update` will create the schema on first boot and `DataInitializer` will reseed the 102 products and the admin user.

### Why use RDS instead of a container

- Automated daily backups + point-in-time restore.
- Managed minor-version patching.
- Storage autoscaling without downtime.
- Survives EC2 instance replacement (the old volume-backed container was tied to the host filesystem).
- TLS in transit, KMS encryption at rest.
- Removes the AL2023/`mysql:8.x` ioctl incompatibility entirely — no more MariaDB workaround.

## S3 — product image storage

| Item | Value |
|------|-------|
| Bucket | `gotokart-product-images-035379289330-us-east-1-an` |
| Region | `us-east-1` |
| Object prefix | `products/` |
| Public read | Yes (bucket policy on `products/*`) |
| Write access | EC2 instance profile only, via IAM policy `GotokartS3ProductImages` |

### IAM policy attached to `ec2-role-iam`

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:DeleteObject", "s3:GetObject"],
      "Resource": "arn:aws:s3:::gotokart-product-images-035379289330-us-east-1-an/products/*"
    }
  ]
}
```

### Bucket CORS (`infra/aws/s3-cors-product-images.json`)

```json
[
  {
    "AllowedHeaders": ["*"],
    "AllowedMethods": ["GET", "PUT", "HEAD"],
    "AllowedOrigins": [
      "https://gotokart.xyz",
      "https://www.gotokart.xyz",
      "http://localhost:3000",
      "http://localhost:5500",
      "http://127.0.0.1:5500"
    ],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3000
  }
]
```

Apply with:

```bash
aws s3api put-bucket-cors \
  --bucket gotokart-product-images-035379289330-us-east-1-an \
  --cors-configuration file://infra/aws/s3-cors-product-images.json
```

### Why we override the S3 endpoint in code

The AWS SDK still defaults to the legacy global hostname (`<bucket>.s3.amazonaws.com`) for `us-east-1`. That hostname **301-redirects** to the regional one for some buckets, and browsers fail CORS preflights through redirects. The backend forces the regional endpoint:

```java
S3Presigner.builder()
    .region(Region.of(region))
    .credentialsProvider(DefaultCredentialsProvider.create())
    .endpointOverride(URI.create("https://s3." + region + ".amazonaws.com"))
    .build();
```

Same override is applied to `S3Client` so deletes also use the regional endpoint.

## EC2 — one-time setup

### 1. Install Docker & plugins

```bash
sudo yum install -y docker git
sudo systemctl enable --now docker
sudo usermod -aG docker ec2-user

sudo mkdir -p /usr/local/lib/docker/cli-plugins
sudo curl -SL "https://github.com/docker/buildx/releases/download/v0.19.3/buildx-v0.19.3.linux-amd64" \
  -o /usr/local/lib/docker/cli-plugins/docker-buildx && \
  sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-buildx
sudo curl -SL "https://github.com/docker/compose/releases/download/v2.33.1/docker-compose-linux-x86_64" \
  -o /usr/local/lib/docker/cli-plugins/docker-compose && \
  sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-compose
exit  # re-login for the docker group
```

### 2. Add swap (prevents OOM on small instances)

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile swap swap defaults 0 0' | sudo tee -a /etc/fstab
```

### 3. Attach the IAM role

In the AWS Console: **EC2 → Instance → Actions → Security → Modify IAM role** and select `ec2-role-iam`.

Verify on the box:

```bash
aws sts get-caller-identity
```

You should see the role ARN, not "Unable to locate credentials".

### 4. Clone repos & configure `.env`

```bash
mkdir -p ~/gotokart && cd ~/gotokart
git clone https://github.com/gotokart/backend.git
git clone https://github.com/gotokart/frontend.git
git clone https://github.com/gotokart/infra.git

cd infra
cp .env.example .env
nano .env       # set RDS_HOST, RDS_USERNAME, RDS_PASSWORD, JWT_SECRET
```

See [AWS RDS — one-time setup](#aws-rds--one-time-setup) for how to provision the database and the `gotokart_app` user before this step.

### 5. First deploy

```bash
docker compose up -d --build
```

On first startup the backend connects to RDS, JPA creates the schema, then `DataInitializer` seeds **102 products** and creates the admin user.

### 6. Issue TLS certs (see [TLS section](#tls--lets-encrypt--nginx-webroot-mode))

## Re-deploy after code changes

SSH in and run:

```bash
cd ~/gotokart && \
  git -C backend  pull origin main && \
  git -C frontend pull origin main && \
  git -C infra    pull origin main && \
  cd infra && docker compose up -d --build
```

There are **no `cp` steps** — the compose file builds `../backend` directly.

If you only changed backend code, force a clean rebuild of just that service:

```bash
docker compose build --no-cache backend && docker compose up -d backend
```

## EC2 Security Group

| Type  | Port | Source       | Purpose |
|-------|------|--------------|---------|
| SSH   | 22   | Your IP      | Management |
| HTTP  | 80   | 0.0.0.0/0    | ACME challenge + redirect to HTTPS |
| HTTPS | 443  | 0.0.0.0/0    | Production traffic |

The EC2 SG ID must also appear as the **source** in the inbound MySQL rule of `gotokart-rds-sg`. The RDS instance itself has no public endpoint.

## CI/CD flow

The `infra/.github/workflows/deploy.yml` workflow triggers on push to `infra/main`:

1. Authenticates to AWS via OIDC (no stored keys).
2. Sends `aws ssm send-command` to EC2.
3. EC2 pulls all repos and runs `docker compose up -d --build`.

Manual trigger is also available from the GitHub Actions UI (`workflow_dispatch`).

Required GitHub secrets: `AWS_IAM_ROLE_ARN`, `AWS_REGION`, `EC2_INSTANCE_ID`.

`EC2_INSTANCE_ID` must match the target instance (`gotokart-ecommerce` in `us-east-1`).
