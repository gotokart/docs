# Backend API

GoToKart's backend is a **Spring Boot 3.4** application exposing REST APIs for authentication (password **and** email OTP), users, products, shopping cart, orders, reviews, and S3-backed product imagery. It is backed by **MySQL** and secured with **JWT**, and sends transactional email through **Brevo SMTP**.

## Stack

- Java 21 · Spring Boot 3.4 · Spring Security · Spring Data JPA
- JJWT 0.11.5 · BCrypt · Maven
- AWS SDK for Java v2 (`software.amazon.awssdk:s3` + `S3Presigner`)
- Spring Mail (`spring-boot-starter-mail`) → Brevo SMTP, async HTML emails

> New to the auth/email features? See **[Auth, email & notifications](notifications)** for the OTP flow, admin domain, and the full notification matrix.

## Base URL

| Environment | Base |
|-------------|------|
| Production  | <code>https://gotokart.xyz/api</code> |
| Local       | <code>http://localhost:8080/api</code> |

The frontend autodetects which one to use; you only ever change it in one place if you're embedding the API elsewhere.

## Authentication

GoToKart issues **JWT** tokens for two login paths: **email OTP** (the default for customers) and **email + password** (used by admins). Passwords are hashed with BCrypt.

### Default admin credentials

| Field | Value |
|-------|-------|
| Email | `admin@gotokart.xyz` |
| Password | `admin123` |
| Role | `ADMIN` |

The admin account is created automatically on backend startup if it does not exist. `admin@gotokart.xyz` is also the inbox that receives all admin notification emails. **Change the password after first login.**

### Using JWT in requests

After login, include the token on every admin request:

```
Authorization: Bearer <your-jwt-token>
```

### Auth endpoints

| Method | Path | Auth | Description |
|--------|------|:---:|-------------|
| `POST` | `/api/auth/otp/request` | No | Email a 6-digit login code |
| `POST` | `/api/auth/otp/verify`  | No | Verify code → JWT (auto-registers new emails) |
| `POST` | `/api/auth/login`       | No | Password login, returns JWT |
| `POST` | `/api/auth/admin/login` | No | Password login restricted to `ADMIN` accounts |
| `POST` | `/api/auth/register`    | No | Password register (always role `USER`), returns JWT |
| `GET`  | `/api/users/me`         | JWT | Get current user profile |

<details>
<summary><strong>POST</strong> <code>/api/auth/otp/request</code> — email a login code</summary>

**Request body**

```json
{ "email": "customer@example.com" }
```

**Response** — `{ "message": "Code sent to customer@example.com" }`

**Notes**

- 6-digit code, 10-minute expiry, 60-second resend cooldown, 5-attempt cap.
- `429` if requested again within the cooldown; `403` if the account is deactivated.
</details>

<details>
<summary><strong>POST</strong> <code>/api/auth/otp/verify</code> — verify code, get JWT</summary>

**Request body**

```json
{ "email": "customer@example.com", "otp": "123456", "name": "Ankit Pandey" }
```

`name` is optional and only used when auto-registering a brand-new email.

**Response** — standard auth payload (`token`, `id`, `name`, `email`, `role`).
</details>

<details>
<summary><strong>POST</strong> <code>/api/auth/admin/login</code> — admin password login</summary>

**Request body**

```json
{ "email": "admin@gotokart.xyz", "password": "admin123" }
```

**Response** — auth payload with `role: "ADMIN"`. Returns `403` if the account is not an admin, so customer credentials can never unlock the admin panel.
</details>

<details>
<summary><strong>POST</strong> <code>/api/auth/register</code> — register new user</summary>

**Request body**

```json
{
  "name": "Ankit Pandey",
  "email": "ankit@gotokart.com",
  "password": "secret123"
}
```

**Response** — same shape as login. Role is **always forced to `USER`** server-side; a client cannot self-register as `ADMIN`.
</details>

## Products

| Method | Path | Auth | Description |
|--------|------|:---:|-------------|
| `GET`    | `/api/products`        | No        | List all products (optionally with `imageKey`) |
| `GET`    | `/api/products/{id}`   | No        | Get product by ID |
| `POST`   | `/api/products`        | ADMIN JWT | Create product (merges stock if name exists) |
| `PUT`    | `/api/products/{id}`   | ADMIN JWT | Update product fields |
| `DELETE` | `/api/products/{id}`   | ADMIN JWT | Delete product (also deletes its S3 image) |

The `Product` entity now carries an `imageKey` field — the S3 object key under the bucket's `products/` prefix. It is optional; products without an image render with a category emoji on the frontend.

<details>
<summary><strong>POST</strong> <code>/api/products</code> — create or merge product</summary>

**Request headers**

```
Authorization: Bearer <admin-jwt-token>
Content-Type: application/json
```

**Request body**

```json
{
  "name": "iPhone 15",
  "description": "Apple iPhone 15 128GB",
  "price": 79999.0,
  "stock": 50,
  "category": { "id": 1 }
}
```

**Notes**

- If a product with the same name already exists, the backend merges/increases stock instead of creating a duplicate row.
- Returns `403 Forbidden` if the `Authorization` header is missing or the user is not `ADMIN`.
- This endpoint does **not** accept an image. Upload it separately — see [Product images](#images).
</details>

<details>
<summary><strong>DELETE</strong> <code>/api/products/&#123;id&#125;</code> — remove product</summary>

**Request headers**

```
Authorization: Bearer <admin-jwt-token>
```

**Notes**

- The S3 object referenced by `imageKey` is deleted as part of this call. If the delete fails (network blip, IAM hiccup) the product still goes — the image is best-effort cleanup.
- If the product is the last one in its category, the category is also removed.
- Ask for explicit confirmation in the frontend before calling this.
</details>

## Product images (S3 presigned uploads)

Image bytes never travel through the JVM. The browser uploads straight to S3 using a short-lived presigned PUT URL minted by the backend.

```text
1. POST /api/products              → product { id }
2. POST /api/products/{id}/image-upload-url?contentType=image/png
                                   → { url, key, contentType, expiresInSeconds, publicUrl }
3. PUT  url   (Content-Type: image/png, body = file bytes)        ← straight to S3
4. PATCH /api/products/{id}/image  body { imageKey: key }
```

| Method | Path | Auth | Description |
|--------|------|:---:|-------------|
| `POST`  | `/api/products/{id}/image-upload-url?contentType=…` | ADMIN JWT | Mint presigned PUT URL |
| `PATCH` | `/api/products/{id}/image`                          | ADMIN JWT | Attach uploaded key to product (also deletes the prior object) |

**Allowed content types:** `image/jpeg`, `image/jpg`, `image/png`, `image/webp`.
The backend validates the type, picks the correct extension, and generates a UUID-based key under `products/`.

<details>
<summary><strong>POST</strong> <code>/api/products/&#123;id&#125;/image-upload-url?contentType=image/png</code></summary>

**Response**

```json
{
  "url": "https://gotokart-product-images-…s3.us-east-1.amazonaws.com/products/3b55…ff.png?X-Amz-…",
  "key": "products/3b55d705-53f8-4b87-b664-4fa85824dcff.png",
  "contentType": "image/png",
  "expiresInSeconds": 300,
  "publicUrl": "https://gotokart-product-images-…s3.us-east-1.amazonaws.com/products/3b55…ff.png"
}
```

**Notes**

- The signed URL is bound to the exact `Content-Type` you sent. The browser must `PUT` with the same header or S3 will reject it.
- The URL targets the **regional** S3 endpoint (`s3.us-east-1.amazonaws.com`) on purpose — the global endpoint redirects, and browsers fail CORS preflights on redirects.
- Default lifetime is **300 seconds**. Tune via the `aws.s3.presign-ttl-seconds` property.
</details>

<details>
<summary><strong>PATCH</strong> <code>/api/products/&#123;id&#125;/image</code></summary>

**Request body**

```json
{ "imageKey": "products/3b55d705-53f8-4b87-b664-4fa85824dcff.png" }
```

**Notes**

- If the product previously had a different `imageKey`, the old object is deleted from S3 after the row is saved.
- Pass `imageKey: null` (or empty string) to remove the image without uploading a new one.
</details>

#### Public read URL

Objects under `products/*` are publicly readable thanks to a bucket policy. The frontend constructs the public URL itself:

```text
https://<bucket>.s3.<region>.amazonaws.com/<imageKey>
```

If you set `aws.s3.public-base-url` (e.g. a CloudFront distribution), the backend uses that prefix instead.

<a id="orders"></a>
## Orders

| Method | Path | Auth | Description |
|--------|------|:---:|-------------|
| `POST`  | `/api/orders/{userId}/place` | No        | Place order (clears cart, decrements stock, emails customer + admin) |
| `GET`   | `/api/orders/{userId}`       | No        | Order history |
| `GET`   | `/api/orders`                | ADMIN JWT | List every order, newest first |
| `PATCH` | `/api/orders/{id}/status`    | ADMIN JWT | Move an order through its lifecycle |

**Order statuses:** `PLACED` → `SHIPPED` → `OUT_FOR_DELIVERY` → `DELIVERED` (or `CANCELLED`). Each change emails the customer an Amazon-style tracker email and notifies the admin.

<details>
<summary><strong>POST</strong> <code>/api/orders/&#123;userId&#125;/place</code></summary>

**Example response**

```json
{
  "id": 11,
  "status": "PLACED",
  "totalAmount": 84999.0
}
```

**Notes**

- On success, immediately refresh cart and orders sections so the user sees the updated state.
- Sends an order confirmation to the customer and a new-order alert to the admin (async, best-effort).
- Each order line snapshots `productImageUrl` so emails show the real product image.
</details>

<details>
<summary><strong>PATCH</strong> <code>/api/orders/&#123;id&#125;/status</code></summary>

**Request body**

```json
{ "status": "OUT_FOR_DELIVERY" }
```

Allowed values: `PLACED`, `SHIPPED`, `OUT_FOR_DELIVERY`, `DELIVERED`, `CANCELLED` (case-insensitive). Invalid values return `400`.
</details>

| Method | Path | Auth | Description |
|--------|------|:---:|-------------|
| `GET`   | `/api/admin/stats`            | ADMIN JWT | Dashboard KPIs + low-stock + recent orders |
| `GET`   | `/api/admin/revenue?period=`  | ADMIN JWT | Time-bucketed revenue (daily/weekly/monthly) |

The backend emails `admin@gotokart.xyz` on new orders, status changes, new signups, new reviews, and low stock, and emails customers their login codes, order confirmations, and status updates. See **[Auth, email & notifications](notifications)** for the complete matrix and SMTP setup.

## Database

Create a database named `gotokart` and configure the JDBC URL, user, and password in `application.properties`. See [Getting started](getting-started) for full examples.

On first startup the backend automatically seeds **102 products** across 11 categories and creates the admin user (`admin@gotokart.xyz`). The schema migrates automatically (`spring.jpa.hibernate.ddl-auto=update`) — including the `image_key` column on `products`, the `product_image_url` snapshot on `order_items`, and the `otp_verifications` table that backs email OTP login.
